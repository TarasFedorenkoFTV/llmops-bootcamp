# Домашні завдання

Шість тижневих ДЗ. Кожне добудовує один шар твого gateway, тож наприкінці курсу маєш
зібраний capstone — окремого «фінального завдання» немає. Місця в коді підписані
`TODO(student, W#)` у `service/Program.cs`. Все робиться на mock, без реального ключа.

Здача: гілка + Pull Request у своєму репозиторії. CI на PR ганяє evals і червоніє на
регресії. В описі PR — що зробив і скрін консолі. Деталі: GETTING_STARTED §11.

Орієнтир по часу: 2–3 години на тиждень після guided lab. Якщо виходить суттєво
більше — принеси питання на Q&A, не закопуйся.

---

## HW1 (після L1–L2): логування + prompt registry

**Завдання**

1. Переконайся, що стек піднімається і кожен запит пише рядок у таблицю `requests`
   (request_id, model, latency, tokens) — це вже працює в стартері, розберися як.
2. Перенеси system-промпт із хардкоду в таблицю `prompts`: сервіс бере активну версію.
3. Пиши версію промпта (`prompt_version`) у кожен лог-рядок.
4. Реалізуй `GET /prompts` (список версій) і `POST /prompts/{version}/activate`
   (promote/rollback).

**Що здаєш:** PR, де чат працює, промпт живе в БД, консоль показує картку Prompt registry.

**Перевірка:** активуй «поганий» промпт (без слова support) → mock відповідає «не знаю»,
evals червоніють; поверни хороший → зелені. Якщо це відтворюється — ти зробив registry
правильно.

## HW2 (після L3–L4): routing + cost

**Завдання**

1. Routing: обирай модель за задачею. Мінімум — два маршрути: звичайні питання →
   дешева (`mock-mini`), повернення/скарги/термінове → сильна (`mock-strong`).
   Обидві вже є в `gateway/litellm-config.yaml`.
2. Cost: заведи табличку цін за 1k токенів, рахуй вартість кожного запиту і пиши в
   `cost_usd`.
3. Реалізуй `GET /cost` → `{ today_usd, budget_usd }` — консоль покаже «Вартість сьогодні».

**Що здаєш:** PR, де в таблиці `requests` видно різні моделі для різних питань і
заповнений `cost_usd`; плитка вартості в консолі жива.

**Перевірка:** напиши боту звичайне питання і «поверніть гроші терміново» — у БД мають
бути дві різні моделі. `SELECT model, count(*) FROM requests GROUP BY model`.

## HW3 (після L5–L6): кеш + інструменти

**Завдання**

1. Кеш відповідей: однаковий запит удруге не має ходити в модель. Ключ —
   модель + промпт + повідомлення. Рахуй hits/misses.
2. Інструменти: коли модель повертає tool_call (`lookup_order`), виконай його і додай
   результат у відповідь. Подумай про timeout і повторний виклик (ідемпотентність).

**Що здаєш:** PR, де другий однаковий запит відповідає миттєво (з кешу), а «Де моє
замовлення #123?» повертає відповідь з результатом інструмента.

**Перевірка:** два однакові запити поспіль — у другого latency ~0ms. Кеш-лічильник
росте (побачиш у HW5 на консолі).

---

## HW4 (після L7–L8): надійність + безпека

**Завдання**

1. Fallback: при 429/5xx від моделі спробуй наступну в ланцюгу; якщо всі впали —
   ввічлива відповідь-заглушка (graceful degradation), а не 500.
2. Circuit breaker: 3 збої поспіль → модель «відкрита» на 30с, запити її пропускають;
   передбач half-open (пробний запит), щоб здоровий провайдер закривав circuit.
3. HITL: незворотна дія (`create_ticket`) не виконується одразу — падає в чергу
   `GET /approvals`, виконується лише після `POST /approvals/{id}/approve`.
4. Guardrail: замаскуй email у вхідному повідомленні перед відправкою в модель.

**Що здаєш:** PR, де `__fail_503` дає ввічливу відповідь (не 500), заявка на тікет
чекає підтвердження в консолі, після approve — виконується.

**Перевірка:** напиши `__fail_503` кілька разів → бот відповідає заглушкою; потім
звичайне питання → за кілька секунд знову нормальна відповідь (half-open спрацював).

## HW5 (після L9–L10): observability + evals

**Завдання**

1. Реалізуй `GET /observability`: requests за сьогодні, p95 latency, error rate — з
   таблиці `requests`; cache-hit % і fallback-лічильник — зі свого коду.
2. Реалізуй `GET /providers` — статус провайдерів для консолі.
3. Розшир golden dataset: додай мінімум 4 власні кейси (позитивні й негативні) у
   `evals/golden.jsonl`, за потреби додай власний grader у `evals/run.py`.

**Що здаєш:** PR, де всі плитки консолі живі (числа, не «—»), і evals проходять з
розширеним датасетом.

**Перевірка:** зроби кілька запитів (включно з повтором і `__fail_503`) — плитки
показують requests, cache-hit > 0, fallback > 0.

## HW6 (після L11–L12): CI-гейт + інцидент

**Завдання**

1. Увімкни eval-гейт у CI: на кожен PR стек піднімається і evals блокують merge при
   регресії (шаблон `.github/workflows/eval-gate.yml` уже є — переконайся, що працює
   в твоєму репозиторії, і підбери поріг під свій датасет).
2. Продемонструй гейт: зроби PR зі зламаним промптом — CI червоний; виправ — зелений.
3. Incident demo: опиши в README свого репо сценарій «інцидент → fallback →
   відновлення» і команди, якими його відтворити (див. приклад в INCIDENT_RUNBOOK
   у репозиторії рішень).

**Що здаєш:** фінальний PR: система збирається `docker compose up`, всі плитки консолі
живі, CI-гейт працює (є червоний і зелений прогін в історії), README з інцидент-демо.

**Перевірка:** ментор клонує твій репозиторій, робить `docker compose up`, проходить
чек-лист із GETTING_STARTED §11.
