CI/CD quality gates, canary і rollback

Зміна промпта — це реліз, повторюємо ми з другого уроку. Сьогодні вона нарешті почне проходити релізний процес: eval-гейт на кожен PR, який фізично не пускає регресію в main. Плюс чесні історії про те, як CI відрізняється від локальної машини, — і rollback-критерії, які пишуться до пожежі.

W1 Основа + промпти→ W2 Routing + cost→ W3 Кеш + tools→ W4 Надійність + безпека→ W5 Observability + evals→ W6 CI + фінал
01

Проблема: перевірка, що залежить від дисципліни

У вас уже є eval, який ловить регресію, — минулий урок закінчився саме цим. Але поки його треба запускати руками — його не запускатимуть. Не зі зла: п'ятниця, дедлайн, «та я ж одне слово поміняв». Усі найгірші регресії заїжджають у main саме так — через маленькі зміни, які «не потребували перевірки». Що менша зміна, то менше бажання її перевіряти — і то важче потім знайти, що саме зламалося.

Гейт у CI знімає це питання назавжди, бо прибирає з ланцюга саме слабку ланку: перевірка більше не залежить від дисципліни. PR зі зламаним промптом фізично не мержиться — не тому, що хтось пильний, а тому, що кнопка merge заблокована. І це змінює не лише якість — це змінює культуру: промпт остаточно стає кодом з усіма наслідками, від рев'ю до заблокованого мержа.

Друга тема сьогодні — про яку рідко думають до першого болю — порядок викочування (блок 06): зміна з зеленими тестами все одно може покласти систему, якщо її компоненти виїхали в неправильній послідовності.

ПринципУсе, що тримається на «не забути», колись буде забуто — питання лише, наскільки дорого. Перевірки, від яких залежить прод, мають запускатися механізмом, а не людиною. Людині лишається найважче: вирішувати, що робити з результатом.
02

Гейт = ваш eval + exit code + CI

Хороша новина: сьогодні ми майже нічого не пишемо. Всі складники гейта вже існують: run.py повертає 0/1 (урок 10), стек піднімається однією командою docker compose up (урок 1), поріг обраний і обґрунтований. CI-система лише виконує це у чистому середовищі на кожен PR і фарбує кнопку merge у колір exit code.

PR відкрито→стек у CI→очікування готовності→python run.py → exit 0/1→merge дозволено / заблоковано

Уся цінність — у словах «на кожен PR». Той самий прогін, який ви робили руками, тепер відбувається завжди: для зміни промпта, для правки роутера, для «я тільки README поправив» (так, і для нього — і це правильно: ви здивуєтесь, скільки разів «правка README» насправді чіпала щось поруч).

Зверніть увагу на архітектурну красу: гейт нічого не знає про LLM. Він знає про exit code. Уся LLM-специфіка — датасет, grader, поріг — інкапсульована в eval-контурі, який ви збудували минулого тижня. Це означає, що гейт не треба буде переписувати, коли зміниться модель, промпт чи навіть провайдер.

Одна адміністративна дрібниця, без якої все це — лише кольорова іконка: сам по собі червоний workflow merge не забороняє. Блокування вмикається в налаштуваннях репозиторію — гілка main захищається, а eval-gate позначається обов'язковою перевіркою (required status check). Шлях: Settings → Branches → Add branch protection rule → Require status checks to pass → вибрати eval-gate. Без цього кроку гейт «радить»; з ним — вирішує. Перевірте це у власному репо, коли робитимете ДЗ тижня 6. Одне застереження: на приватному репозиторії безкоштовного плану branch protection може бути недоступний — тоді гейт лишається «радником», і це треба чесно зазначити в PR.

03

Розтин workflow: кожен крок — це граблі

Відкрийте .github/workflows/eval-gate.yml у стартері. Читаємо як послідовність відповідей на конкретні болі:

- name: Up stack (без UI — для evals не потрібен)
  run: docker compose up -d --build service

- name: Wait for service
  run: |
    for i in $(seq 1 40); do
      if curl -sf http://localhost:8080/health; then exit 0; fi
      sleep 5
    done
    echo "service did not become healthy"; docker compose logs; exit 1

- name: Wait for gateway (холодний LiteLLM дає 500 на перший запит)
  run: |
    # POST-проба у /v1/chat/completions, поки не прийде 200

- name: Evals
  env: { SERVICE_URL: http://localhost:8080 }
  run: python evals/run.py --dataset evals/golden.jsonl --threshold 5

- name: Logs on failure
  if: failure()
  run: docker compose logs

- name: Down
  if: always()
  run: docker compose down -v

Пройдімося: стек піднімається без UI — evals ходять в API, збирати фронтенд у CI — марні хвилини. Очікування сервісу — цикл із 40 спроб, і всередині if curl; then, а не curl && exit — чому саме так, розповість блок 04. Окреме очікування gateway — теж не з теорії. Logs on failure — бо червоний прогін без логів це загадка, а з логами — діагноз. Down з if: always() — прибрати за собою навіть після падіння. І про --threshold 5: це число — частина датасету, а не константа шаблона; після ДЗ тижня 5 у наборі ~10 кейсів — поріг у workflow оновлюється разом із ним (правило: N−1 при N≤10, далі 85% з округленням угору). Перевірка «поріг відповідає розміру датасету» — гарний кандидат у механічні перевірки гейта (блок 07).

04

CI — це інше середовище, і воно вас здивує

З практики

Чесна історія з підготовки цього курсу. Локально гейт працював ідеально. Перший запуск у GitHub Actions упав за 57 секунд. Причина виявилася в тому, що Actions виконує кроки з bash -e: перший же невдалий curl у циклі очікування вбивав крок цілком — хоча локально той самий цикл спокійно ретраїв, поки сервіс прокидався. Звідси та сама форма if curl; then у workflow — невдала проба стає умовою, а не помилкою.

Другий сюрприз: холодний старт LiteLLM у CI давав 500 на найперший запит — локально ви цього не бачите, бо поки відкриваєте браузер, gateway встигає прогрітися. У CI між up і першим запитом — мілісекунди. Довелося додати явне очікування готовності gateway — POST-пробу до самого ендпоінта, а не просто health-check.

З практикиТаких сюрпризів у CI-інтеграціях назбирується колекція — ще один із моєї практики на великій платформі: крок пайплайна смикав зовнішню систему і вважав виклик невдалим, хоча та чесно виконала роботу, — просто відповіла редиректом 303 замість очікуваного 200, і перевірка «код == 200» фарбувала здоровий прогін у червоне. Успіх у HTTP — це діапазон і контракт, а не одне магічне число. Формула для всіх подібних граблів однакова: точна умова успіху, явні очікування готовності, і жодних припущень, що чуже середовище поводиться як ваш ноутбук.

В історії PR нашого репозиторію так і лишилися: два червоні прогони, потім зелений. Це не сором — це процес: гейт теж код, і він теж проходить налагодження. Мораль одна:

ЛайфхакГейт треба прогнати на реальному CI до того, як він комусь заблокує реліз. «Працює локально» для CI-конфіга означає рівно нічого: інший шел-режим, інші тайминги, холодні старти. Відкрийте тестовий PR і подивіться на прогін — п'ятнадцять хвилин, які збережуть вам довіру команди до гейта.
05

Червоний гейт — подарунок

Тепер про культуру. Червоний гейт на вашому PR — це неприємно: ви поспішали, а вас зупинили. Правильна рамка: гейт щойно зловив регресію до користувачів, а не після. Він зробив за секунди те, що інакше зробила б підтримка за тиждень скарг: знайшов, що «маленька правка» ламає поведінку. Червоне — це найдешевший момент дізнатися.

Але культурна рівновага тут крихка, і руйнується вона одним способом:

Типова помилкаЗмержити повз червоний гейт «бо терміново». Одна така історія — і гейта немає: наступний, кому червоно і терміново, згадає прецедент, і за місяць гейт — це прапорець, який усі обходять. Якщо гейт справді помилково червоний — лагодьте гейт (флейковий кейс, поріг), у тому ж PR або окремим. Обхід — ніколи; винятки з правила «якість блокує merge» не масштабуються.

І дзеркальне правило для авторів гейта: тримайте його швидким і чесним. Гейт, що йде двадцять хвилин або падає через флейки, викликає законне роздратування — і його знесуть з аргументом «він заважає працювати». Швидкий, стабільний, зрозумілий у падінні — три властивості, які купують гейту довге життя.

Сучасний контекст, який робить цей урок ще актуальнішим: у 2026-му значна частина змін у репозиторій приходить від агентів — код, промпти й конфіги генеруються асистентами, а PR відкриваються автоматикою. Обсяг змін зростає, а увага рев'юера — ні. Це не аргумент проти агентів; це аргумент за те, що механічний гейт стає єдиним, що масштабується: людина фізично не перечитає все, а eval-прогін перечитає щоразу однаково. На платформі, яку я супроводжую, саме тому гейти й політики перевірок росли паралельно з часткою агентних змін — і кожен «зелений» PR від асистента проходив ту саму планку, що й людський.

З практикиІ фінальний штрих культури гейтів, підтверджений практикою: у гейта є життєвий цикл, і він закінчується. На платформі, де я працюю, ми окремими свідомими рішеннями зносили перевірки, що втратили функцію: тимчасовий гейт релізного циклу, який пережив свою причину, і правило підтверджень, що стало інертним після зміни процесу. Гейт, який завжди зелений і нічого не захищає, — не безплатний: він додає хвилини кожному PR і, гірше, привчає сприймати гейти як шум. Тимчасовим перевіркам — дату перегляду; мертвим — видалення тим же ритуалом, що й народження: PR, рев'ю, пояснення чому.

«Швидкий» — це конкретні хвилини, і на них можна впливати. У нашому workflow найдорожчий крок — --build: збірка образів з нуля на кожен прогін. Перші кроки оптимізації відомі: піднімати лише потрібні контейнери (ми вже прибрали UI — це мінус ціла збірка фронтенду), кешувати шари образів між прогонами засобами CI, тримати eval-прогін коротким (наш набір кейсів — це секунди; час з'їдає стек, не evals). Орієнтир простий: гейт має бути швидшим за каву — тоді на нього не шкода чекати і немає спокуси обходити.

06

Порядок викочування — частина релізу

Зелений гейт каже: «цей стан системи здоровий». Він не каже: «шлях від старого стану до нового безпечний». Якщо зміна зачіпає кілька компонентів, деплой у неправильному порядку ламає систему навіть з ідеальними тестами: компонент А вже шле нове поле, компонент Б ще не вміє його читати — і привіт, помилки на проді при двох «здорових» версіях.

У нашому стеку це питання виникає, щойно зміна перетинає межі: нова колонка в БД + код, що її пише (спершу міграція, потім код); нове ім'я моделі в конфізі gateway + роутер, що на нього шле (спершу конфіг, потім роутер); новий формат відповіді сервісу + консоль, що його читає (спершу сервіс із сумісністю, потім споживач).

Правило сумісностіЗагальний шаблон: спершу деплоїться той, хто читає (навчений розуміти і старе, і нове), потім той, хто пише нове. Проміжний стан — коли в системі живуть обидві версії — має бути робочим, бо ви в ньому обов'язково побудете: хвилину при штатному релізі або годину при відкаті половини.

У повній формі цей шаблон називають expand → migrate → contract: спершу розширити (додати нове поле/колонку поряд зі старим, обидва працюють), потім мігрувати (перевести споживачів на нове), і лише в кінці звузити (прибрати старе — окремим релізом, коли лог підтверджує, що старим ніхто не користується). Три нудні кроки замість одного сміливого — і кожен з них можна відкотити окремо. Сміливий один крок теж можна відкотити — разом з усім, що встигло зламатися.

07

Вимикач без деплою — і артефакти, що їдуть разом

Гейт не пускає погану зміну в main. Порядок викочування береже вас від зламаного проміжного стану. Лишається третє питання, яке ставлять під час інциденту: як вимкнути щось прямо зараз, не чекаючи збірки.

У світі промптів на це є дві різні відповіді, і їх варто не плутати. Відкат версії в реєстрі (урок 2) повертає попередню поведінку — це операція над вмістом: одна активація, секунди, слід в audit trail. Feature flag — це вимикач над механізмом: обійти кеш, вимкнути маршрутизацію на дорогу модель, перевести систему в режим «тільки ввічлива заглушка», відключити tool-виклики цілком. Перше відповідає на «промпт зламався», друге — на «зламався або дорого коштує сам механізм».

Технічно прапорець — це рядок у таблиці або значення в конфізі, який читається на кожному запиті (з коротким кешем, щоб не бити базу). Дорослий вигляд у нього такий:

  • Значення за замовчуванням — безпечне. Прапорець недоступний або база не відповіла → система працює в безпечному режимі, а не падає.
  • Зміна прапорця — теж подія, з автором і часом. Інакше через тиждень ніхто не пояснить, чому кеш вимкнений уже п'ятий день і хто це зробив.
  • Кожен прапорець має термін життя. Найтиповіша хвороба: прапорці накопичуються, і за рік ніхто не знає, які комбінації взагалі протестовані. Прапорець без плану видалення — це технічний борг з таймером.
Типова помилкаПрапорець як заміна релізному процесу. Спокуса зрозуміла: замість гейтів і рев'ю — «викотимо вимкненим і потихеньку ввімкнемо». Проблема в тому, що код за вимкненим прапорцем не перевіряється ніяк: він не проходить eval'и, бо не виконується, і вмикається вперше в проді. Прапорець — це аварійний вимикач і засіб поступового ввімкнення, а не спосіб обійти перевірку якості.

Промпт, код і схеми — один реліз

Друга половина цього блоку продовжує тему порядку викочування, але з іншого боку: сумісність артефактів. У LLM-системі поведінка визначається не лише кодом. Її задають щонайменше чотири речі: код control plane, версія промпта в реєстрі, схеми інструментів і набір eval-кейсів із порогом. Вони живуть у різних місцях — і саме тому легко розходяться.

Класичний сценарій розходження виглядає так. Ви додали інструмент і згадали про нього в новій версії промпта. Промпт активували (це одна кнопка, урок 2), а код із новим інструментом ще не в проді. Модель сумлінно просить інструмент, якого не існує; система відповідає помилкою на цілком легітимне прохання. І навпаки: код виїхав, промпт лишився старим — новий інструмент є, але модель про нього не знає, і функціональність просто не працює, тихо й без помилок.

ПринципЯкщо зміна торкається двох артефактів — вона одна зміна, а не дві. Практично це означає: новий інструмент і промпт, що його згадує, їдуть одним PR разом з eval-кейсом, який перевіряє їхню пару; порядок активації описаний у самому PR (спершу код, потім промпт — бо код зі зайвим інструментом безпечний, а промпт із неіснуючим — ні); а якщо активація промпта робиться руками після мержу, це рядок у чек-листі релізу, а не річ, яку хтось згадає.

І перевірка, яка ловить цей клас проблем автоматично: eval-кейс на кожну пару «промпт + механізм». Кейс «питання про замовлення повертає результат інструмента» червоніє і тоді, коли зламали промпт, і тоді, коли зламали інструмент, — саме тому він цінніший за два окремі юніт-тести. Ваш golden dataset з уроку 10 уже так і влаштований: він перевіряє систему, а не компоненти.

У гейті живуть не тільки evals

Eval-прогін ловить регресію поведінки. Але в LLM-системі є цілий клас поломок, які до моделі навіть не доходять, — і вони ловляться дешевими механічними перевірками в тому самому workflow. Кожна з них — кілька рядків, і кожна колись зекономить вечір:

ПеревіркаЩо ловить
Шаблон промпта містить усі очікувані плейсхолдери, і жодного невідомого{servce} замість {service} — підстановка тихо не відбувається, у модель їде текст із дужками
Схеми інструментів — валідний JSON Schemaзламану схему провайдер відкине вже на проді
Прайс покриває всі моделі з конфіга gatewayдодали модель, забули ціну → cost_usd тихо стає null, і облік бреше (урок 4)
Моделі в конфізі запінені, а не alias'и«регресія без коміта» від оновлення провайдера (урок 3)
У діфі немає ключів і секретівнайдорожча помилка з найкоротшим фіксом

Логіка тут та сама, що з пірамідою тестів: найдешевше — механічні перевірки конфігів і схем, дорожче — eval-прогін зі стеком, найдорожче — модельні перевірки з реальним ключем. Ставте їх у цьому порядку, і 80% поломок ловитимуться за секунди, не піднімаючи жодного контейнера.

З практикиЯ на цьому вчився дорогою ціною: гейт, який перевіряв лише «змістовну» частину, спокійно пропустив реліз, де в конфізі з'явилася модель без ціни. Формально все зелене — eval'и проходили, тести проходили. Помітили через тиждень, коли хтось спитав, чому в звіті вартості дірка рівно з тієї дати. Найдорожчі поломки майже завжди такі: не «система не працює», а «система тихо перестала знати правду про себе».
Що з цього в ДЗПрапорці в ДЗ тижня 6 не вимагаються — обов'язкове там інше: увімкнений гейт, доказ «червоний → зелений», інцидент-демо і план rollout. Цей блок — про те, що ви робитимете в наступній системі: аварійний вимикач і правило «одна зміна = один реліз» коштують дешево, поки їх закладають на старті, і дорого, коли по них уже сумували під час інциденту.
08
опційно

Canary для промптів

Гейт перевіряє зміну до релізу на золотому наборі. Але золотий набір — це 10–20 кейсів, а прод — тисячі живих запитів. Опційна техніка для обережних релізів — canary: нова версія промпта отримує 10% трафіку, стара — 90%. Далі порівнюєте метрики двох груп — а метрики у вас є з тижня 5: error rate, fallback, вартість, і скарги як фінальний суддя. Добре — розкатуєте на всіх; погано — rollback однією командою, якою ви володієте з тижня 1.

Найприємніше — скільки тут нового коду: майже нуль. Механіка розподілу трафіку — той самий routing з уроку 3, тільки критерій не «тип задачі», а «відсоток запитів» (найпростіше — за хешем ідентифікатора сесії, щоб той самий користувач стабільно бачив ту саму версію). Версії промпта — реєстр з уроку 2. Порівняння метрик — зрізи по prompt_version у лозі, який ви ведете з уроку 1. Canary — це не інструмент, який купують; це композиція механізмів, які ви вже збудували.

І чесне попередження про межі: canary потребує обсягу. 10% трафіку — це скільки запитів на годину у вашій системі? Якщо три, порівняння метрик двох груп — це ворожіння на шумі: різниця в error rate між «одна помилка» і «нуль помилок» нічого не означає. На малому трафіку чесніша стратегія — гейт до релізу плюс швидкий rollback після: ви все одно дізнаєтесь про проблему швидко, просто від усіх користувачів одразу, а не від десятої частини. Canary окупається там, де десята частина — це вже статистика.

План (розділення трафіку, метрики порівняння, критерії promote/rollback) — опційна частина ДЗ тижня 6; реалізація — для найзавзятіших.

09

Rollback-критерії пишуться заздалегідь

Останній шматок релізної дисципліни — найдешевший і найчастіше пропущений. Перед викочуванням будь-якої значущої зміни відповідь на питання «коли смикаємо назад» має бути записана. Формула проста:

Відкочуємо, якщо:
  eval pass rate < 5/6            (прогін після деплою)
  або fallback_events зростає     протягом 15 хв
  або error rate > 5%             протягом 15 хв
Хто смикає: черговий, без погоджень.
Як: POST /prompts/{stara}/activate — одна команда.

Чому заздалегідь: під час інциденту думати пізно — під час інциденту треба виконувати. Записаний критерій знімає найдорожчу розмову поганого вечора: «може, ще почекаємо? ніби вирівнюється...». Не вирівнюється. Критерій пробитий — відкат, розбір завтра. А «одна команда» в останньому рядку — це вимога до архітектури, яку ви вже виконали: rollback за секунди існує з уроку 2.

10

Лабораторна: гейт у бою

  1. Розібрати workflow. Прочитати eval-gate.yml крок за кроком: checkout → compose up без UI → wait service → wait gateway (тепер ви знаєте чому) → evals → логи при падінні → down. Пояснити собі кожен крок.
  2. Червоний прогін. Гілка зі зламаним промптом → PR → Actions червоніє. Подивитися лог прогону в CI: ті самі 3/6, що ви бачили локально на минулому уроці, — тепер їх бачить кнопка merge.
  3. Зелений прогін. Полагодити промпт у тій самій гілці → пуш → гейт зеленіє → merge. В історії PR лишаються обидва прогони — це і є доказ, що гейт працює (і рівно це ментор перевірятиме у ДЗ тижня 6). Як має виглядати результат — живий demo-PR у репозиторії еталонів: червоний прогін, фікс, зелений. Уточнення: demo-PR — це ілюстрація формату (червоний прогін → зелений), а не еталон рішення тижня; зроблений він на скороченій базі, тож діф не збігатиметься з твоїм.
  4. Rollback-критерії. Написати свої: три умови, хто смикає, якою командою. Покласти поруч із fallback-порядком і budget-політикою — ваша папка операційних рішень майже зібрана.
  5. Опційно: canary на папері. План: як розділити трафік 90/10 своїм роутером, які метрики порівнювати між групами, критерії promote/rollback.
Перевір себе (обов'язкова доріжка):
  • у твоєму репо є червоний і зелений прогін гейта;
  • можеш пояснити кожен крок workflow — і навіщо окреме очікування gateway;
  • rollback-критерії записані до викочування, з командою відкату;
  • розумієш, чому порядок деплою залежних компонентів — частина релізу.
Пригадай з минулих тижнів (без підглядання):
  • чому поріг evals — не 100%, і яку сліпу пляму має N−1? (урок 10)
  • які чотири частини в правильного алерту? (урок 9)
  • чому незворотна дія не виконується «бо модель попросила»? (уроки 6 і 8)

Антипатерни тижня

  • Eval, який запускають руками «коли не забудуть». Його не запускатимуть — див. блок 01.
  • Мержити повз червоний гейт «бо терміново». Одна така історія — і гейта немає.
  • Гейт, ніколи не проганяний на реальному CI. Перший запуск — на чужому терміновому PR. Дякуємо, не треба.
  • Викочування без rollback-критеріїв. Під час інциденту треба виконувати, а не дискутувати.
  • Ігнорувати порядок деплою залежних компонентів. Зелені тести не рятують від неправильної послідовності.
