# Гайд ментора: перевірка ДЗ

Ментор на потоці один (часто це той самий, хто веде курс). Мета документа — щоб рішення
«зараховано / на доопрацювання» було швидким і однаковим з тижня в тиждень,
а перевірка не з'їдала вечори. Повні технічні критерії кожного тижня —
у таблицях «Що перевіряє ментор» у `starter/homework/hwN.md`; тут — процес і
рішення, які таблиці не покривають.

## Процес

1. Студент кидає посилання на PR у канал потоку (репозиторій — публічний або
   приватний з тобою в колабораторах). Дедлайн здачі — **за 24 год до
   наступного заняття**; пізніші PR перевіряються за SLA наступного тижня.
2. SLA перевірки — **до наступного заняття** (тобто ~2–3 доби).
   Кожне hwN гілкується від main **після мержа hwN−1**: якщо в diff видно
   попередній тиждень — попроси ребейз, таймер SLA на паузі.
3. Результат — коментар у PR: заповнена чек-таблиця тижня (✓/✗) + вердикт
   **«зараховано»** або **«на доопрацювання»** з переліком пунктів.
4. Повторна здача перевіряється **лише по повернутих пунктах**.
5. Третя ітерація по тому самому ДЗ — далі не листування: коротка розмова
   голосом на найближчому занятті (швидше і людяніше).

## Скільки часу закладати

| ДЗ | Орієнтир | Як економити |
|---|---|---|
| hw1 | 15–20 хв/студента (з підйомом стека — перша здача) | після першого разу студент знає формат артефактів, далі перевірка швидша |
| hw2–hw5 | 10–15 хв/студента | перевіряй з артефактів у PR (скрін консолі, SQL-вивід, опис рішень); підйом стека — при будь-якому ✗ чи сумніві |
| hw4 (пік) | 10–15 хв/студента, але **очікуй здачу двома комітами** (reliability → safety) і за потреби оголоси **подовжений SLA (+2 доби)** — це найважчий тиждень (fallback+HITL+PII в одному PR), пік закладений свідомо; приймай половину, якщо друга ще в роботі | reliability-половина перевіряється без черги approvals; safety-половину дивись, коли доїде — не повертай усе через незакриту другу половину |
| hw6 | 20–30 хв/студента; **на потік 25 це чесні 10–12 год** — заклади під це окремі 2–3 вечори або оголоси для hw6 подовжений SLA (5 діб) | чистий клон + `docker compose up --build` обов'язково; перевіряй потік однією сесією — docker-кеш шарів робить кожен наступний build швидшим |

Критерії приймання для студентів — незмінні протягом потоку: вони відкриті
у файлах ДЗ, і студенти на них спираються. Якщо стабільно не вкладаєшся в
час — ріж глибину власної перевірки (вибірковість: які рядки перевіряти
підйомом стека, які — з артефактів PR), і зафіксуй зміну тут, щоб наступний
тиждень мірявся так само. Зміни самих критеріїв — правкою файлів ДЗ між
потоками, не всередині потоку.

## Глибина перевірки (щоб рішення були однакові з тижня в тиждень)

- **hw1 і hw6 — повний підйом стека обов'язково** (перша здача і фінал).
- **hw2–hw5 — перевірка з артефактів PR** (скріни консолі, SQL-виводи, опис
  рішень); стек піднімаємо вибірково і **завжди** — при будь-якому ✗ чи сумніві.
- Критерій повернення №1 («стек не піднімається») застосовний лише якщо стек
  піднімали.

**Підйом стека студента** (обов'язковий ритуал, інакше чужий том Postgres дасть
хибні результати):

```bash
gh pr checkout <url-PR>        # або clone + fetch гілки
docker compose down -v         # ОБОВ'ЯЗКОВО: чистий стан від попереднього студента
docker compose up --build
# ПРОГРІВ — частина ритуалу, не опція: 1–2 запити в чат перед будь-якими
# поведінковими перевірками. Холодний gateway валить перші запити (status=0),
# і це виглядає як дефект здачі: err=100%, cache-hit=0, evals 0/N.
# ...перевірки зі шпаргалки...
docker compose down -v
```

**Кумулятивні здачі і регресія минулих тижнів.** Таблиця тижня N не бачить,
що код тижня N зламав властивість тижня N−1 (класика: кеш w3 із ключем без
промпта мовчки ламає rollback-демо w1 — і evals це маскують, бо кейси
віддаються з кешу). Тому негативні рядки минулих тижнів, чий механізм
зачеплений діфом поточного тижня, виконуються повторно; мінімум для hw3+ —
рядок «Ключ кешу повний» із hw3.

## Критерії ПРИЙОМУ (коротко)

Тижневі таблиці — у `hwN.md`. Наскрізні правила поверх них:

- Зараховано = **всі обов'язкові** рядки таблиці тижня ✓.
- Обов'язкова доріжка самодостатня: відсутність опційної частини **ніколи**
  не є підставою для повернення чи зниження оцінки.
- Інший підхід, ніж в еталоні, — **ок**, якщо критерії проходять. Еталон —
  референс, а не єдина правильна відповідь.
- Еталонні бранчі для звірки: `llmops-bootcamp-solutions`, `w1`…`w6`.
- **«Артефакт є — властивості немає»** — головний клас халтури, який чекові
  таблиці не ловлять самі по собі: кеш, що ніколи не влучає; черга approvals
  «для звіту» при тікеті, створеному одразу; `/providers`, прибитий до `ok`;
  дефолт промпта, що маскує поломку реєстру; `continue-on-error` у гейті.
  Ловиться **негативними рядками** тижневих таблиць (тепер вони є в кожному
  `hwN.md`) — виконуй їх завжди: вони перевіряють властивість, а не наявність.

## Критерії ПОВЕРНЕННЯ (на доопрацювання)

Повертаємо, якщо є хоча б одне:

1. **Стек не піднімається** командою `docker compose up --build` (з чистого
   клону для hw6; для hw1–hw5 — з гілки PR). Застосовний лише якщо стек не
   піднімається **через здачу**: зайняті порти на **твоїй** машині (типово
   `8080`/`5432`) — не критерій; у такому разі піднімайся з файлом зсунутих
   портів зі стартера або власним override (пам'ятай про `!override` для
   списків `ports` — Compose їх зливає при мержі).
2. **Обов'язковий критерій тижня не проходить** — у коментарі обов'язково:
   яку команду виконав, що очікував, що отримав (щоб студент відтворив).
   Сюди ж належить **порожній опис PR** там, де рядок таблиці вимагає опис
   (hw3 «Операційні рішення»): це не «PR неперевірний» (критерій 5), а
   непройдений рядок — повертай за критерієм 2 із проханням дописати опис
   або розділ у README.
3. **Evals червоні** без пояснення в описі PR (усвідомлений червоний з
   поясненням «чому і що далі» — привід для розмови, не для мовчазного
   повернення). Перш ніж повертати, виключи **власний холодний старт**:
   прогрій стек і прожени ще раз — 0/N на щойно піднятому стеку майже завжди
   твій прогрів, а не регресія студента. Виняток: одразу після серії
   `__fail_503` evals червоні через **опційний** circuit breaker — це наслідок
   добре зробленої опційної роботи, не підстава для повернення; почекай до
   закриття breaker'а і прожени знову (див. hw4, рядок «Evals»).
4. **Секрети в коді** (реальні ключі, паролі поза `.env`) — повертати одразу,
   з поясненням і проханням invalidate ключа. Це найтерміновіший кейс.
   Примітка: дев-пароль `Password=llmops` у `docker-compose.yml` — це стартер,
   не порушення; критерій — про **реальні** секрети (ключі провайдерів,
   продакшн-паролі).
5. **PR технічно неперевірний**: конфлікт з main, CI-гейт не запустився,
   force-push після початку рев'ю стер контекст коментарів — повертаємо без
   розбору змісту, з одним рядком «що полагодити, щоб перевірка стала можливою».
6. **Копія еталона без власної спроби.** Ознаки: один коміт, відсутність слідів
   власних ітерацій, а головне — підпис еталона в коді:
   `grep -c "\[W1\]\|\[W2\]\|\[W3\]\|\[W4\]\|\[W5\]\|РЕФЕРЕНС" service/Program.cs` —
   маркери `[W1]`…`[W5]` і шапка «РЕФЕРЕНС (кумулятивно)» є лише в еталоні
   (у чесній здачі — 0). Кількість влучань **залежить від тижня** (маркери
   накопичуються кумулятивно: ~6 на `w1`, ~15 на `w6`) — тому дивись на факт
   «нуль vs є маркери», а не на конкретне число. Побайтову ідентичність із бранчем
   `wN` не шукай — її не буває (у бранчі еталона є файли, яких у репозиторії
   студента бути не може). Дія — не звинувачення, а розмова: «поясни голосом,
   як працює X» на наступному занятті. Мета курсу — навички, копіпаст краде
   їх лише у студента.

**НЕ підстава для повернення** (лишається коментарем-порадою): розмір PR сам по собі (але >~800 рядків змін поза темою тижня — попроси винести окремим PR), стиль коду,
іменування, «я б зробив інакше», відсутність тестів, будь-що з опційної
доріжки, дрібні недоліки, що не валять критерії.

## Формат фідбеку

- Чек-таблиця тижня з ✓/✗ — завжди, навіть коли все зелене (студент бачить,
  що перевірено все, а не «глянув по діагоналі»).
- До кожного ✗ — **як відтворити**: команда + очікуване + фактичне.
- Максимум **3 головні зауваження** текстом; решта — інлайн-коментарі в код.
  Стіна з 15 пунктів демотивує і не читається.
- Опційну доріжку, якщо зроблена, — відзнач окремим рядком. Це безкоштовна
  мотивація найсильніших.
- Тон: розбираємо код, не людину. За зразком постмортема з L12 — «чому
  критерій пропустив», а не «чому ти не зробив».

## Тижнева шпаргалка верифікації

Мінімальний набір команд, якщо перевіряєш підйомом стека
(усі — з кореня репо студента; SQL — через
`docker compose exec postgres psql -U llmops -d llmops -c "…"`):

> **Прогрів правильно — і чому «одного запиту» замало на w4–w6.** Спершу
> **дочекайся готовності gateway** (полль `POST http://localhost:8080/…` або
> gateway `/v1/chat/completions`, поки не поверне `200`), і лише ТОДІ прогрівай
> та жени evals. Якщо прогрівати наосліп, ранні виклики падають на холодному
> gateway — і на тижнях із circuit breaker (w4–w6) ці падіння **відкривають
> breaker**, після чого весь прогін ~30 с сидить у заглушці: `error_rate=100%`,
> `cache_hit=0`, evals `0/N` — виглядає як тотальна регресія, якої немає. Це
> комбо «холодний старт × breaker», не дефект здачі. Рецепт: дочекайся 200 →
> кілька запитів, поки один не відповість по суті (не фіксований лік — стільки,
> скільки треба) → якщо перед цим летіли `__fail_503` або холодні падіння,
> почекай ~30 с до закриття breaker'а і лише тоді жени evals.

| ДЗ | Швидка верифікація | Еталон |
|---|---|---|
| hw1 | `GET /prompts` → 2 версії, одна active (seed із міграції, том чистий); `activate v99` → 404; activate v1 → «не знаю» → v2; `SELECT prompt_version FROM requests ORDER BY created_at DESC LIMIT 3`; evals: червоні на v1 → зелені на v2 (команда — GETTING_STARTED §6) | `w1` |
| hw2 | звичайне + «поверніть гроші терміново» → `SELECT model, count(*) … GROUP BY model` → 2 моделі; `SELECT cost_usd … WHERE cost_usd > 0 LIMIT 3`; `GET /cost`; fallback-порядок зафіксовано (константа/коментар біля роутера) | `w2` |
| hw3 | те саме питання двічі → у свіжішого рядка `requests` `prompt_tokens = 0` і `cost_usd = 0` (повтор не ходив у модель; `latency_ms` на mock нічого не доводить — промах теж <50 мс); «Де моє замовлення #123?» → результат інструмента; рев'ю коду: лічильники hit/miss окремо; опис PR: timeout + ключ ідемпотентності | `w3` |

| hw6 | чистий клон → up --build (зайняті порти на твоїй машині — піднімайся з файлом зсунутих портів, це не ✗ студенту); Actions: червоний і зелений прогін; гейт живий на поданому стані (**обов'язково живий злам промпта** → червоний чек; `grep continue-on-error` → нуль — але grep не ловить `\|\| true`, тому живий злам не пропускати); блокування merge: `gh api repos/<owner>/<repo>/branches/main/protection --jq '.required_status_checks.contexts'` → містить `eval` (404 = protection немає → гейт «радить», а не блокує; легально лише з чесною позначкою в PR); інцидент-демо з `INCIDENT_RUNBOOK.md` відтворюється (питання відновлення — нове, не з кешу); README: 30-day rollout (4 кроки); поріг гейта ≥ правила з hw5 (N−1 при N≤10; далі 85% з округленням угору) у двох місцях — нижчий без обґрунтування = повернення | `w6` + demo-PR #1 |

## Рубрика «30-day rollout» (hw6)

Зараховано = кожен із 4 кроків називає **практику курсу + конкретну дію у своїй
команді**. «Впровадимо evals» — ні. «Тиждень 1: golden set на 10 кейсів з
реальних тікетів нашого саппорту» — так.

## Червоні прапорці (сигнал правити курс, а не студентів)

- Той самий обов'язковий критерій валиться у >2 студентів потоку — правити
  треба завдання/стартер, а не повертати всім підряд.
- Студент двічі поспіль здає копію еталона — розмова голосом, без третьої
  ітерації листування.
- Перевірка стабільно виходить за орієнтири часу — ріж глибину власної
  перевірки (див. «Скільки часу закладати») і фіксуй зміну в цьому файлі;
  критерії для студентів усередині потоку не змінюються.
