# Гайд ментора: перевірка ДЗ

Ментор на потоці один (часто це сам автор курсу). Мета документа — щоб рішення
«зараховано / на доопрацювання» було швидким і однаковим з тижня в тиждень,
а перевірка не з'їдала вечори. Повні технічні критерії кожного тижня —
у таблицях «Що перевіряє ментор» у `starter/homework/hwN.md`; тут — процес і
рішення, які таблиці не покривають.

## Процес

1. Студент кидає посилання на PR у канал потоку (репозиторій — публічний або
   приватний з тобою в колабораторах). Дедлайн здачі — **за 24 год до
   наступного заняття**; пізніші PR перевіряються за SLA наступного тижня.
2. SLA перевірки — **до наступного заняття** (тобто ~2–3 доби).
   Кожне hwN гілкується від main **після мержа hwN−1**: якщо в diff видно
   попередній тиждень — попроси ребейз, таймер SLA на паузі.
3. Результат — коментар у PR: заповнена чек-таблиця тижня (✓/✗) + вердикт
   **«зараховано»** або **«на доопрацювання»** з переліком пунктів.
4. Повторна здача перевіряється **лише по повернутих пунктах**.
5. Третя ітерація по тому самому ДЗ — далі не листування: коротка розмова
   голосом на найближчому занятті (швидше і людяніше).

## Скільки часу закладати

| ДЗ | Орієнтир | Як економити |
|---|---|---|
| hw1 | 15–20 хв/студента (з підйомом стека — перша здача) | після першого разу студент знає формат артефактів, далі перевірка швидша |
| hw2–hw5 | 10–15 хв/студента | перевіряй з артефактів у PR (скрін консолі, SQL-вивід, опис рішень); підйом стека — при будь-якому ✗ чи сумніві |
| hw6 | 20–30 хв/студента; **на потік 25 це чесні 10–12 год** — заклади під це окремі 2–3 вечори або оголоси для hw6 подовжений SLA (5 діб) | чистий клон + `docker compose up --build` обов'язково; перевіряй потік однією сесією — docker-кеш шарів робить кожен наступний build швидшим |

Якщо стабільно виходить довше — правила твої: спрощуй критерій або ріж
глибину перевірки, і зафіксуй зміну тут, щоб наступний тиждень мірявся так само.

## Глибина перевірки (щоб рішення були однакові з тижня в тиждень)

- **hw1 і hw6 — повний підйом стека обов'язково** (перша здача і фінал).
- **hw2–hw5 — перевірка з артефактів PR** (скріни консолі, SQL-виводи, опис
  рішень); стек піднімаємо вибірково і **завжди** — при будь-якому ✗ чи сумніві.
- Критерій повернення №1 («стек не піднімається») застосовний лише якщо стек
  піднімали.

**Підйом стека студента** (обов'язковий ритуал, інакше чужий том Postgres дасть
хибні результати):

```bash
gh pr checkout <url-PR>        # або clone + fetch гілки
docker compose down -v         # ОБОВ'ЯЗКОВО: чистий стан від попереднього студента
docker compose up --build
# ...перевірки зі шпаргалки...
docker compose down -v
```

## Критерії ПРИЙОМУ (коротко)

Тижневі таблиці — у `hwN.md`. Наскрізні правила поверх них:

- Зараховано = **всі обов'язкові** рядки таблиці тижня ✓.
- Обов'язкова доріжка самодостатня: відсутність опційної частини **ніколи**
  не є підставою для повернення чи зниження оцінки.
- Інший підхід, ніж в еталоні, — **ок**, якщо критерії проходять. Еталон —
  референс, а не єдина правильна відповідь.
- Еталонні бранчі для звірки: `llmops-bootcamp-solutions`, `w1`…`w6`.

## Критерії ПОВЕРНЕННЯ (на доопрацювання)

Повертаємо, якщо є хоча б одне:

1. **Стек не піднімається** командою `docker compose up --build` (з чистого
   клону для hw6; для hw1–hw5 — з гілки PR).
2. **Обов'язковий критерій тижня не проходить** — у коментарі обов'язково:
   яку команду виконав, що очікував, що отримав (щоб студент відтворив).
3. **Evals червоні** без пояснення в описі PR (усвідомлений червоний з
   поясненням «чому і що далі» — привід для розмови, не для мовчазного
   повернення).
4. **Секрети в коді** (реальні ключі, паролі поза `.env`) — повертати одразу,
   з поясненням і проханням invalidate ключа. Це найтерміновіший кейс.
5. **PR технічно неперевірний**: конфлікт з main, CI-гейт не запустився,
   force-push після початку рев'ю стер контекст коментарів — повертаємо без
   розбору змісту, з одним рядком «що полагодити, щоб перевірка стала можливою».
6. **Копія еталона без власної спроби.** Ознаки: один коміт, побайтова
   ідентичність із бранчем `wN`, відсутність слідів власних ітерацій. Дія —
   не звинувачення, а розмова: «поясни голосом, як працює X» на наступному
   занятті. Мета курсу — навички, копіпаст краде їх лише у студента.

**НЕ підстава для повернення** (лишається коментарем-порадою): розмір PR сам по собі (але >~800 рядків змін поза темою тижня — попроси винести окремим PR), стиль коду,
іменування, «я б зробив інакше», відсутність тестів, будь-що з опційної
доріжки, дрібні недоліки, що не валять критерії.

## Формат фідбеку

- Чек-таблиця тижня з ✓/✗ — завжди, навіть коли все зелене (студент бачить,
  що перевірено все, а не «глянув по діагоналі»).
- До кожного ✗ — **як відтворити**: команда + очікуване + фактичне.
- Максимум **3 головні зауваження** текстом; решта — інлайн-коментарі в код.
  Стіна з 15 пунктів демотивує і не читається.
- Опційну доріжку, якщо зроблена, — відзнач окремим рядком. Це безкоштовна
  мотивація найсильніших.
- Тон: розбираємо код, не людину. За зразком постмортема з L12 — «чому
  критерій пропустив», а не «чому ти не зробив».

## Тижнева шпаргалка верифікації

Мінімальний набір команд, якщо перевіряєш підйомом стека
(усі — з кореня репо студента; SQL — через
`docker compose exec postgres psql -U llmops -d llmops -c "…"`):

| ДЗ | Швидка верифікація | Еталон |
|---|---|---|
| hw1 | `GET /prompts` → 2 версії, одна active; activate v1 → «не знаю» → v2; `SELECT prompt_version FROM requests ORDER BY created_at DESC LIMIT 3`; evals: червоні на v1 → зелені на v2 (команда — GETTING_STARTED §6) | `w1` |
| hw2 | звичайне + «поверніть гроші терміново» → `SELECT model, count(*) … GROUP BY model` → 2 моделі; `SELECT cost_usd … WHERE cost_usd > 0 LIMIT 3`; `GET /cost`; fallback-порядок зафіксовано (константа/коментар біля роутера) | `w2` |
| hw3 | те саме питання двічі → друге < 50 мс (поле `latency_ms` у відповіді `/chat`); «Де моє замовлення #123?» → результат інструмента; опис PR: timeout + ключ ідемпотентності | `w3` |
| hw4 | `__fail_503` → ввічлива заглушка власного тексту; рев'ю коду: виклик у циклі по ланцюгу + лічильник; «поверніть гроші» → заявка в `GET /approvals` → approve → тікет; повторний approve → no-op | `w4` |
| hw5 | кілька запитів (з повтором і `__fail_503`) → усі 6 плиток з числами; `git diff` по `golden.jsonl` → ≥4 нові кейси з негативними і **жодного видаленого** | `w5` |
| hw6 | чистий клон → up --build; Actions: червоний і зелений прогін; інцидент-демо з README відтворюється; README: 30-day rollout (4 кроки); поріг гейта ≥ правила N−1/85% з hw5 — нижчий без обґрунтування = повернення | `w6` + demo-PR #1 |

## Рубрика «30-day rollout» (hw6)

Зараховано = кожен із 4 кроків називає **практику курсу + конкретну дію у своїй
команді**. «Впровадимо evals» — ні. «Тиждень 1: golden set на 10 кейсів з
реальних тікетів нашого саппорту» — так.

## Червоні прапорці (сигнал правити курс, а не студентів)

- Той самий обов'язковий критерій валиться у >2 студентів потоку — правити
  треба завдання/стартер, а не повертати всім підряд.
- Студент двічі поспіль здає копію еталона — розмова голосом, без третьої
  ітерації листування.
- Перевірка стабільно виходить за орієнтири часу — спрощуй критерій і фіксуй
  зміну в цьому файлі.
